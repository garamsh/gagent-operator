# Agent

The `agent.garam.sh` API group, the `Agent` kind it serves, and the controller that reconciles it.

## Current decisions

- `Agent` is served at `agent.garam.sh/v1alpha1` and is namespaced. Its types live in `api/v1alpha1/` and its reconciler in `internal/controller/` — the paths the kubebuilder CLI owns.
- `AgentSpec` carries what an agent needs to run: the container image, the Secret its credential material comes from, the persistent volume it keeps state on, and the compute resources its container asks for. `AgentStatus` carries observed state only, and nothing a user writes.
- The image reference is required and has no default. No registry or tag convention exists for the agent image and neither project owns one, so the field asks rather than invents; a default can be added later to a field that already exists.
- Credential material is referenced, never carried. The Secret is created outside this operator, and the workload mounts its keys as files — key material does not travel through environment variables.
- The Pod carries a supplementary group, and the credential files are readable by that group rather than by their owner alone. A Secret volume's files are owned by root, so an owner-only mode leaves them unreadable to an agent that drops root — and the operator cannot know which uid an agent image runs as. A group needs no such knowledge: the kubelet puts every volume of the Pod under it and hands it to each container's initial process, whatever user that container runs as. It reaches no further on its own — a descendant that drops its supplementary groups leaves the group behind, and the credential with it. The same group is what makes a freshly provisioned state volume writable where the provisioner does not hand it over. Measured on 2026-08-24, on a volume a `csi.proxmox.sinextra.dev` StorageClass provisioned: the mounted directory is owned by root at mode 2775 with the Pod's group, and the container's own uid, which is neither root nor that gid, writes to it.
- What that gives up: any container of the Pod that mounts the credentials volume can read it, where an owner-only mode would have required it to run as root. The workload has one container, and which containers mount that volume is the operator's to decide.
- A file the workload requires to be owner-only does not come from a volume the kubelet writes while the Pod carries the group. Whatever mode is asked for, owner-read and group-read are added to what the kubelet writes into that volume, so the tightest a file gets is `0440`. A volume the kubelet does not write into — one an init container fills after the mount is set up — delivers the mode asked for, owned by the writing container's uid; which side resolves the constraint is open, and §Open questions holds both.
- Nothing mounted today needs that. `gagent@757dd26:internal/config/owner_only.go:17` carries the rule, and applies it to its config file and its TLS server key; this operator mounts neither, and the per-agent client credential it does mount is not subject to it.
- The workload is a StatefulSet of one replica with a volume claim template for the agent's volume.
- An Agent's name is bounded at 52 characters, and the API server is what refuses a longer one. The workload's Pods carry that name with a suffix in a label — the longest is the revision hash, up to 11 characters — and a label value stops at 63. A name the API server took and the workload could not use would leave the controller building a StatefulSet whose Pods the API server then refuses, with nothing to retry.
- An Agent whose credentials Secret is absent gets no workload at all, and the Secret's arrival is what builds it. Mounting a Secret that does not exist leaves the Pod unable to start, and creating that Secret is not an edit to the Agent, so the controller watches the Secret rather than waiting to be woken by a spec change.
- No field of `v1alpha1` names an external system. What the operator needs to reach `garam` is process configuration — the machine listener's address, the certificate the operator authenticates with, that certificate's key, and the file the listener is verified against — and an unset address leaves it making no outbound call at all.
- The operator reads the definitions `garam` holds for it on an interval and claims each one `garam` holds no claim for. The read is scoped by the certificate the connection authenticated as, so it names nothing this operator is not named in. The poll runs beside the reconcilers as a manager `Runnable` and not inside one: the clock wakes it and no event on an `Agent` does.
- The certificate the operator authenticates with is read at each handshake, and each call opens its own connection so that there is one. Expiry is the whole of `garam`'s revocation, so a certificate loaded once stops authenticating on a schedule. What rewrites that file is nothing this operator does and nothing it obliges — see §Open questions.
- What the listener is verified against is a file the deployment supplies, and not the organization issuer an operator's own certificate arrives beside: that authority signs this operator and a different one signs `garam`. Verification is never skipped, under a flag or otherwise.
- A claim `garam` refuses as a conflict is terminal. A definition is claimed once, so nothing retries the refusal and the next read reports the definition as claimed.
- A claimed agent GRN is reported in `AgentStatus` and never written in `AgentSpec`, and the field arrives with the change that first fills it. `garam` is where a claim is durable — a read answers the claim state — so this operator can lose its status entirely and still learn what it holds.
- Nothing links a claimed definition to an `Agent`. The values a definition carries name neither the image nor the storage size `AgentSpec` requires, so a claim creates no object and binds none — see §Open questions.
- The reconciler owns the StatefulSet through an owner reference and holds no finalizer: deleting the Agent is what removes the workload.
- An Agent reports one condition, `Synced`: whether the cluster carries the workload the spec asks for, and the reason where it does not. `status.observedGeneration` says which generation that answer was computed from, so a status the controller has not caught up with is visible as one. A spec this controller cannot act on is reported there rather than returned as an error, because an error would requeue forever and say nothing on the object.
- The object reports nothing about whether the agent is running. The controller does not read the workload's health, and a condition claiming readiness it has not observed would be worth less than none.

## Rationale

The layout and the generated manifests follow the scaffold, per [ADR 0001](adr/0001-kubebuilder-go-v4-scaffold.md): code is written to fit the CLI's paths rather than the CLI's output being reshaped to fit a preferred layout.

The workload's form is [ADR 0005](adr/0005-statefulset-of-one.md): a StatefulSet of one replica, because the agent's state is a single-writer store and the ordering guarantee is the only thing keeping two writers off one volume.

The image field was settled on issue #11, before the API was written, and carries no ADR: the rule is stated in the field's own doc comment, where it is enforced. "No outbound call in `v1alpha1`" was settled there too, as a milestone boundary rather than a project rule. ADR 0007 is where that boundary was crossed, and no field of the API moved when it was — which is what the boundary was drawn for.

The Pod's group and the group-readable mode are [ADR 0006](adr/0006-credential-group.md), settled on issue #31 after the e2e layer measured what no layer below it could see: a container that drops root cannot read an owner-only file the kubelet wrote as root. Its erratum of 2026-08-23 narrows what the group reaches, without moving the decision.

How the operator reaches `garam` is [ADR 0007](adr/0007-claim-definitions-from-a-poller.md), settled on issue #2 once `garam`'s own ADR-0033 decided the surface: a poll rather than a watch, a claim that binds the operator to the agent GRN a definition minted, and a second claim that is a conflict rather than an override. What it decides here is where the poll runs, what the operator authenticates as, what it verifies `garam` against, and where a claimed GRN is reported.

The condition this API reports was settled on issue #14, and carries no ADR for the same kind of reason: its type and its reasons are constants in `api/v1alpha1`, and the field's own doc comment names them where a user of the API reads them.

## Open questions

- **Whether a definition supplies everything an `Agent` needs, or only its composition.** A definition's values are `map[string]string`, keys of 1 to 64 characters of lowercase letters, digits and `-`, values of at most 4096 bytes, at most 32 entries, and `garam` interprets none of it: the keys expected are `model`, `system-prompt`, `workspace`, `model-credential`, `repo-credential`, and a credential key carries a credential's name and never its value. None of them is the image reference or the storage size `AgentSpec` requires. Either the values gain those keys and this operator creates the `Agent` from a claimed definition, which puts the choice of image in front of a console user; or a definition composes an `Agent` something else created — a person, a chart, a controller above this one — and the claim binds what already exists. The first makes `garam`'s console the whole of the API's surface; the second leaves two places to look for one agent. The answer is `garam`'s contract as much as this repository's, and until it lands a claim creates no object here.
- **What rewrites the certificate this operator authenticates with.** It is read at each handshake, which is what a short lifetime needs, and `garam` publishes no revocation list so expiry is the whole of its revocation. Re-reading delivers nothing on its own: a file nothing rewrites reads the same until it expires, and that is indistinguishable from working rotation until the day it stops. No renewal mechanism exists here and no obligation on the deployment is stated anywhere — `garam`'s own #483 carries a renewal path for an agent, and whether an operator's certificate travels one is not settled.
- **What this operator reports back to `garam`.** A claim says an operator holds an agent; nothing here says the agent runs. `garam`'s API separates provisioning state from runtime state and expects them from different parties, and this operator reports neither.
- **How a file `gagent` requires owner-only reaches the Pod, once one is mounted.** Two remedies stand and nothing measured chooses between them. This operator can deliver such a file from a volume the kubelet does not write into, which costs an init container and a copy tool in the agent image. Or `gagent` can narrow a rule that no longer separates what it was written to separate: where it drops a shell child to a second uid it drops the Pod's group with it, so a root-owned `0440` file is already closed to that child, and where it runs the child under its own account instead, an owner-only mode closes nothing to it either. Neither is needed while no such file is mounted, and the choice is not this operator's alone.
- **No layer here refuses a mode `gagent` would.** The e2e suite runs a substitute image, and a substitute brings its own acceptance rules. A workload that applied that rule could not stand in for it either: pointed at the credentials this operator mounts, it refuses `0440` and fails the suite against a correct operator. What closes the gap is a fixture that refuses the file the rule governs, once such a file is mounted.
- **Resizing an agent's volume.** A StatefulSet's claim template is immutable after creation, so a change to `spec.storageSize` on an existing `Agent` cannot be satisfied by editing the workload. ADR 0005 accepts the limitation without answering it. The controller leaves the claim as it is and says so on the object, which makes the limitation visible without answering it either.
