# Agent

The `agent.garam.sh` API group, the `Agent` kind it serves, and the controller that reconciles it.

## Current decisions

- `Agent` is served at `agent.garam.sh/v1alpha1` and is namespaced. Its types live in `api/v1alpha1/` and its reconciler in `internal/controller/` — the paths the kubebuilder CLI owns.
- `AgentSpec` carries what an agent needs to run: the container image, the Secret its credential material comes from, the persistent volume it keeps state on, and the compute resources its container asks for. `AgentStatus` carries observed state only, and nothing a user writes.
- The image reference is required and has no default. No registry or tag convention exists for the agent image and neither project owns one, so the field asks rather than invents; a default can be added later to a field that already exists. Who it asks is the operator's deployer and not the agent's author: an agent's definition says what the agent is, and what container that is built from is this operator's to decide.
- Credential material is referenced, never carried. The Secret is created outside this operator, and the workload mounts its keys as files — key material does not travel through environment variables.
- The Pod carries a supplementary group, and the Secret is projected readable by that group rather than by its owner alone. A Secret volume's files are owned by root, so an owner-only mode leaves them unreadable to a container that drops root — and the operator cannot know which uid an arbitrary image runs as. A group needs no such knowledge: the kubelet puts every volume of the Pod under it and hands it to each container's initial process, whatever user that container runs as. It reaches no further on its own — a descendant that drops its supplementary groups leaves the group behind, and the credential with it. The same group is what makes a freshly provisioned state volume writable where the provisioner does not hand it over. Measured on 2026-08-24, on a volume a `csi.proxmox.sinextra.dev` StorageClass provisioned: the mounted directory is owned by root at mode 2775 with the Pod's group, and the container's own uid, which is neither root nor that gid, writes to it.
- The agent does not read that projection. `garam`'s adapter is what reads the agent's private key, in a sidecar of the agent's pod, and it refuses a key file any group or other bit is set on and refuses one owned by another user (`garam@1ff8346:internal/keyfile/keyfile.go:30-41`); `garam` publishes both halves as a deployment contract and refuses to relax them (`garam@1ff8346:docs/architecture/deployment-contract.md` §What the binary enforces about key material). A volume the kubelet writes satisfies neither half — the tightest mode it delivers under the group is `0440`, and the owner is root whatever is asked for.
- So an init container copies each projected file into a memory-backed volume the kubelet does not write, at a mode only its owner can reach, and the agent mounts that copy and not the projection. The group is what lets the init container read the projection, and memory is what keeps the copy off the node's disk.
- The Pod names one user and every container runs as it, so the copy's owner is whoever reads it. The operator names that user rather than being told it: an owner is one value for a whole Pod, and a uid taken off any one image stops being that value as soon as a second image in the Pod reads the same file. What an agent's image owes in exchange is stated on `spec.image`, where a user of the API reads it.
- The image the init container runs is this operator's own configuration and is required of every deployment, because every agent's Pod carries that container — an `Agent` a user wrote as much as one this operator constructs. It needs a shell and `install` and nothing of the agent; the agent's own image cannot stand in, `gagent`'s being distroless (`gagent@e9c12a5:build/agent.Dockerfile`).
- What that gives up: an agent image that cannot run as the user the Pod names cannot be run at all, where a group asked nothing of the image; and any container of the Pod reads the copy, because they all run as its owner. The workload has one container beside the init container, and which containers mount that volume is the operator's to decide.
- The copy is made once, at pod start. A credential replaced in the Secret afterwards reaches the projection and not the file the process reads, so replacing one is a restart.
- The workload is a StatefulSet of one replica with a volume claim template for the agent's volume.
- The workload is one a namespace enforcing PodSecurity `restricted` admits. The Pod asserts `runAsNonRoot` beside the user ADR 0010 named — naming a user the standard would accept is not the same as asserting one — and names the runtime's default seccomp profile; each container drops every capability and the right to gain a privilege. Those are the four the standard asks for and the four it refuses a Pod without, and none takes anything from a workload of this shape: the init container runs `install` and the agent runs whatever it runs. What they ask of an agent's image is stated on `spec.image`, and no flag offers any of them — the audience for one is the deployer already told the image must run as uid 65532. Measured on `garam-dev` on 2026-08-26, in a namespace labelled `pod-security.kubernetes.io/enforce=restricted`: the workload this operator builds was admitted and its Pod ran, with the credential arriving at mode 600 owned by the uid that read it; the same workload without those four fields had its Pod refused on all four, so what is admitting it is the security context and not the namespace.
- `readOnlyRootFilesystem` is set on neither container. It is no part of `restricted`, so nothing refuses the workload without it, and it is the one field of the Pod's security context this operator has not decided.
- An Agent's name is bounded at 52 characters, and the API server is what refuses a longer one. The workload's Pods carry that name with a suffix in a label — the longest is the revision hash, up to 11 characters — and a label value stops at 63. A name the API server took and the workload could not use would leave the controller building a StatefulSet whose Pods the API server then refuses, with nothing to retry.
- An Agent whose credentials Secret is absent gets no workload at all, and the Secret's arrival is what builds it. Mounting a Secret that does not exist leaves the Pod unable to start, and creating that Secret is not an edit to the Agent, so the controller watches the Secret rather than waiting to be woken by a spec change.
- No field of `v1alpha1` names an external system. What the operator needs to reach `garam` is process configuration — the machine listener's address, the certificate the operator authenticates with, that certificate's key, and the file the listener is verified against — and an unset address leaves it making no outbound call at all.
- The operator reads the definitions `garam` holds for it on an interval and claims each one `garam` holds no claim for. The read is scoped by the certificate the connection authenticated as, so it names nothing this operator is not named in. The poll runs beside the reconcilers as a manager `Runnable` and not inside one: the clock wakes it and no event on an `Agent` does.
- The certificate the operator authenticates with is read at each handshake, and each call opens its own connection so that there is one. Expiry is the whole of `garam`'s revocation, so a certificate loaded once stops authenticating on a schedule. What rewrites it is the operator itself, by renewing.
- That credential lives in one place: a Secret mounted into the manager's Pod, read as files and replaced through the API server. The Pod carries the same supplementary group the agent's workload does and the volume is mounted group-readable, because the kubelet writes those files as root whatever user the container runs as. Nothing copies the credential from a delivery into a working file, so nothing can seed it a second time and lose a renewal; the out-of-band mint places the Secret once, and re-placing it is both the recovery and what takes the lineage back.
- The read path and the write path are different on purpose. The operator learns its credential from the mounted file and reaches the API only to write a renewal, so it holds `patch` on that one Secret by name and neither `get` nor `list`. Both keys move in one patch, because a handshake reads a certificate beside the key it was issued with.
- The renewal runs beside the poll as a second `Runnable` and not inside it: the two answer to different clocks, and a call one makes should not hold the other's up. Both join the manager's leader-election group, and for the renewal that is load bearing rather than tidy — `garam` renews the certificate it last issued and refuses every other, so two processes renewing one identity leave the loser holding one it can never renew again. One identity is held by one process.
- The operator does not compute the renewal window; it asks on an interval and reads the kind of what comes back. A refusal meaning "too early" is not a failure, one meaning "superseded" is reported as needing a mint out of band, and nothing here restates the fraction `garam` measures the window by. The interval sits far below that window and far above the delay between a renewal being stored and the process reading it back.
- A certificate the window closed on fails at the handshake and stops nothing. The poll goes on failing and saying why, and the renewer says which refusal it met; a poller stopped instead would remove the only signal.
- The renewal is unset until a deployment asks for it, as the address is: no Secret named, no renewal, and the volume is optional so a deployment given no identity still starts.
- What the listener is verified against is a file the deployment supplies, and not the organization issuer an operator's own certificate arrives beside: that authority signs this operator and a different one signs `garam`. It holds whatever `garam` presents, and what that is has already moved once: the leaf `garam-dev` served until 2026-08-26, and since then a `garam` machine server root that signs it and is a separate certificate. The flag is named for its role so that only the file's contents move, which is what happened. Verification is never skipped, under a flag or otherwise.
- A claim `garam` refuses as a conflict is terminal. A definition is claimed once, so nothing retries the refusal and the next read reports the definition as claimed.
- A definition says what the agent is and this operator says how an agent is built. Composition is `garam`'s — the model, the system prompt, the workspace, the tool set, the names of credentials — and construction is this operator's: the image, the storage size, the security context, the scheduling. So `AgentSpec` keeps `image` and `storageSize` required and the operator supplies them: no value of a definition names either. What decided that beyond the division is that a console user choosing an agent's container is choosing what this operator runs as a root-capable workload in a cluster they cannot see, and `v1alpha1` carries no override for one.
- A definition's values carry the composition this operator can deliver, and the operator reads a closed set of keys out of them rather than carrying the map. That set holds one key family today: an agent's tool set, declared as one key per tool naming that tool's pin, with the pin opaque to this operator and the key name its contract. `values` is free-form and `garam` refuses no key, so an operator that carried the whole map would leave the prohibition on reading an image resting on nobody typing one. What the closed set costs is that a definition declares only what this operator has been taught, which is the cost `AgentSpec` already pays. Nothing here reads a value yet: the mechanism arrives with the change that first carries one.
- The directory an agent loads its tools from is this operator's to set and is declared in no value. A path inside a container this operator chose is construction, and a definition naming it would point the agent at a directory whose contents its author controls.
- A value this operator does not understand is ignored and reported where the poll's per-pass detail is reported, and construction goes on. Refusing over a value that by construction has no meaning here would turn a typo in a console field into an agent that never runs, and a definition carrying a stray key reports it on every pass because a poll has no memory. A tool set that is absent leaves nothing placed and no default invented: an empty pin set and no pin set are different inputs, and what either means is the agent's to decide, as `spec.image` having no default is the same rule one layer out.
- A tool set reaches the workload as a file and this operator writes no environment variable for it. The pins resolve from a file, and `GAGENT_TOOLS_PINS` makes the agent refuse to start with an error naming the operator: measured against `gagent`'s entry point on 2026-08-26, recorded on `gagent#745`, and holding while that issue is open. An environment road opened there would leave this decision standing on one road being cheaper than two rather than on the measurement, and that is the claim to re-check when it closes. That this operator already places a file is a convergence and not the reason. The file is public, so it takes neither the memory-backed copy nor the owner-only mode an agent's credential takes.
- What carries a tool set to the workload is the `Agent`'s spec, so an `Agent` a person wrote declares one the same way as one this operator constructs. The reconciler reads the `Agent` and nothing else, and a field only the poller could fill would make a constructed agent a different kind of thing from a written one.
- The free-form map does not travel past the boundary that reads it. What `garam` answers is parsed once where it is read and what moves on is the selection, so the constructor holds no map and cannot name an image key — a rule kept by a type rather than by a reader's restraint. That is what admits a definition to the constructor at all, which today is given an agent's GRN and its credential and nothing the definition carries.
- A definition declares an agent's pins and cannot declare its required tool set. No configuration in `gagent` reaches it — `gagent@ff9a2dc:internal/tool/registry.go:22` holds it and `gagent@ff9a2dc:cmd/gagent/agent.go:116` passes it — so this operator reads no key for one: a key it accepted and could not deliver would report success while nothing changed. That `message_send` is mandatory is an intended invariant of `gagent`'s ADR 0009, an agent that cannot report being fail-closed by design (received on 2026-08-27 rather than read at a commit), which settles why the required set exists and not whether it should be reachable.
- A claimed agent GRN is reported in `AgentStatus` and never written in `AgentSpec`, and the field arrives with the change that first fills it. `garam` is where a claim is durable — a read answers the claim state — so this operator can lose its status entirely and still learn what it holds.
- Where the operator supplies the image and the storage size from is its own configuration, one of each for every agent it constructs, and neither has a default. An operator given `garam`'s address and neither refuses to start: one that claimed agents it could not build would hold them away from an operator that could. What would settle a second answer is a second agent needing a different image, or a person who is not the deployer needing to choose one.
- The poller constructs an agent for every definition it holds a claim on, not only for the one it claimed on that pass. `garam` reports a claim for as long as the definition exists, so construction driven by a fresh claim alone would build nothing after a restart.
- An agent's credential comes from `garam` on the route the claim admits this operator to, and is asked for only where what comes back can be stored at once. `garam` generates the private key per certificate and keeps none, so the store is what makes a credential obtained: nothing asks for one it already has somewhere to put, and a write that fails is answered by another certificate rather than by another write. A credential kept in this process to be retried is one only this process has.
- What is read to answer whether an agent's credential is placed is the Secret holding it, never the `Agent` beside it. The `Agent` is created first so the Secret is owned by it and goes when it goes, so a refused placement leaves an `Agent` standing with no key anywhere; read as constructed, that credential would be gone with nothing left to ask again.
- The Secret carries the certificate, the private key, the authority that signed it, and the root `garam`'s listener is verified against, each under its own key. The last two are different certificates and the wrong one fails at the handshake: an agent that pinned the issuer could not reach `garam` at all. `garam` answers when the certificate stops being valid, so nothing here parses a PEM to learn it.
- This operator places an agent's first credential and replaces none. An agent renews its own over the connection that credential authenticated, and this operator's route is what recovers one that expired — it answers again at any time, with no window and no lineage to lose, which is not how this operator's own identity behaves.
- A refusal of an agent's certificate means "not mine right now" and construction stops there. `garam` answers the same for an agent held by another operator, for one this operator was replaced on, and for one that does not exist, so there is nothing to tell apart and nothing to retry against.
- The epoch is met at the certificate route and nowhere else. A claim reported against a definition is whichever assignment exists, so it survives a reassignment and says nothing about who holds the agent. This operator does not poll for its own dispossession: a credential already placed means no call is made, so it learns it was replaced the next time it needs one, and it tears nothing down on that.
- An `Agent` the operator constructs is named for the digest of the whole agent GRN, and the Secret is named after the `Agent`. The name reads no part of the GRN — what its segments mean is `garam`'s — so nothing here moves if that format does. Both names are the operator's: the definition carries neither.
- A constructed agent is built in the namespace the manager runs in. That is what keeps the power to create a Secret to one namespace rather than to the cluster.
- The agent GRN an `Agent` was constructed for is reported in `AgentStatus`, and is empty on an `Agent` a user wrote. `garam` is where a claim is durable — a read answers the claim state — so this operator can lose its status entirely and still learn what it holds.
- The reconciler owns the StatefulSet through an owner reference and holds no finalizer: deleting the Agent is what removes the workload.
- The poller and the reconciler both write an `Agent`'s status, and both write through a patch. The fields are disjoint — the poller reports the agent GRN, the reconciler the condition and the generation it was computed from — but the writes are not: an update carries the resource version the object was read at, so a report landing between a reconcile's read and its write is refused, and the reconcile fails on a race that resolves itself. A merge patch carries no resource version and names only the fields its writer decided, which is what makes disjoint fields disjoint writes. Measured on `garam-dev` on 2026-08-26, one report racing each of 40 reconciles: an update was refused 27 times and a patch none.
- An Agent reports one condition, `Synced`: whether the cluster carries the workload the spec asks for, and the reason where it does not. `status.observedGeneration` says which generation that answer was computed from, so a status the controller has not caught up with is visible as one. A spec this controller cannot act on is reported there rather than returned as an error, because an error would requeue forever and say nothing on the object.
- The object reports nothing about whether the agent is running. The controller does not read the workload's health, and a condition claiming readiness it has not observed would be worth less than none.

## Rationale

The layout and the generated manifests follow the scaffold, per [ADR 0001](adr/0001-kubebuilder-go-v4-scaffold.md): code is written to fit the CLI's paths rather than the CLI's output being reshaped to fit a preferred layout.

The workload's form is [ADR 0005](adr/0005-statefulset-of-one.md): a StatefulSet of one replica, because the agent's state is a single-writer store and the ordering guarantee is the only thing keeping two writers off one volume.

The image field was settled on issue #11, before the API was written, and carries no ADR: the rule is stated in the field's own doc comment, where it is enforced. "No outbound call in `v1alpha1`" was settled there too, as a milestone boundary rather than a project rule. ADR 0007 is where that boundary was crossed, and no field of the API moved when it was — which is what the boundary was drawn for.

The Pod's group and the group-readable mode are [ADR 0006](adr/0006-credential-group.md), settled on issue #31 after the e2e layer measured what no layer below it could see: a container that drops root cannot read an owner-only file the kubelet wrote as root. Its erratum of 2026-08-23 narrows what the group reaches, without moving the decision.

How a file its reader must own reaches that Pod is [ADR 0010](adr/0010-copy-an-agents-credential-into-a-memory-volume-the-pods-own-user-owns.md), settled on issue #82 once `garam` published the rule as a contract and refused the branch where the reader narrows it. It does not supersede ADR 0006 and nothing in ADR 0006 is false: that decision carries the projection into the Pod, and this one carries it from the projection to a reader that must own it. It is also where ADR 0006's rejected uid field is reopened and rejected again, for a second reason — the operator names the Pod's user instead of being told the image's. Its shape was measured on `garam-dev` under PodSecurity `restricted` before it was built, with two controls that separate the rule's two halves.

How the operator reaches `garam` is [ADR 0007](adr/0007-claim-definitions-from-a-poller.md), settled on issue #2 once `garam`'s own ADR-0033 decided the surface: a poll rather than a watch, a claim that binds the operator to the agent GRN a definition minted, and a second claim that is a conflict rather than an override. What it decides here is the division between what a definition says and what this operator builds, where the poll runs, what the operator authenticates as, what it verifies `garam` against, and where a claimed GRN is reported.

What rewrites the operator's own credential is [ADR 0008](adr/0008-renew-the-operator-credential-into-the-secret-it-is-read-from.md), settled on issues #74 and #76 once `garam`'s ADR-0046 gave an operator a route to renew over the connection it already holds. It closes ADR 0007's open question with a mechanism: one home for the credential, replaced through the API server rather than as a file, which is what lets a process that can write nothing on its own disk replace what it authenticates with. Its route was undeployed in `garam` when the decision was made and is deployed now, which the ADR records as two dated measurements rather than as a prediction.

What a claimed definition becomes is [ADR 0009](adr/0009-construct-a-claimed-agent-from-the-operators-own-configuration.md), settled on issues #75 and #79 together because neither can be built without the other's answer: an `Agent` needs an image, a storage size and a credential, and a definition carries none of the three. It decides where the first two come from, when the certificate route is called and what becomes of the answer, who names the objects, and where the epoch is met. Its route was measured on `garam-dev` before it was built, which is where the facts about the two roots, the unfenced re-issue and the unbranchable refusal come from.

Where an agent's tool set is declared is [ADR 0012](adr/0012-declare-an-agents-tool-set-in-its-definitions-values.md), settled on issue #92. It extends ADR 0009 rather than superseding it: the sentence "no value of a definition names either, and none is read" decides the image and the storage size, and its reason — the audience a container choice asks — does not reach a value that chooses among the tools an image already carries. What it adds to the division is the other half of it: which values this operator carries, what becomes of the ones it does not, and how one reaches a Pod. It landed with no mechanism and nothing here reads a value yet, because both peer projects sequenced the declaration site ahead of the code that would carry it.

The condition this API reports was settled on issue #14, and carries no ADR for the same kind of reason: its type and its reasons are constants in `api/v1alpha1`, and the field's own doc comment names them where a user of the API reads them.

What the workload's security context carries was settled on issue #85 and carries no ADR: `restricted` is a published standard rather than a choice this project makes, and the four fields it asks for were left undecided by ADR 0006 on a ground — that each constrains what a user's image may be — which holds for one of them and not for the four. That one is left open below.

That both writers of an `Agent`'s status patch was settled on issue #84, and carries no ADR because it changes no division: the poller reported the GRN before it and reports it now. What moved is the reconciler's write. It is recorded here because the reasoning that cleared the race in review — that disjoint fields do not race — was wrong, and the first live run is what found out; the next claim about which writes race on this object is to be tested against a cluster.

## Open questions

- **What rewrites the file `garam`'s listener is verified against.** ADR 0008 replaces the certificate this operator presents and leaves this one alone: a renewal answers with the `garam` server root beside the credential, and taking it would make the operator rewrite what it verifies `garam` by out of an answer that root was used to verify. What the deployment supplies stays the deployment's until something decides otherwise.
- **What this operator reports back to `garam`.** A claim says an operator holds an agent; nothing here says the agent runs. `garam`'s API separates provisioning state from runtime state and expects them from different parties, and this operator reports neither. ADR 0012 gives it a second subject: a value this operator ignored is reported in this operator's log and a pin an agent cannot satisfy in the agent's, and neither log is one a definition's author reads.
- **Whether an agent's required tool set should be reachable from configuration at all.** Nobody has answered it. `gagent` holds the invariant deliberately, which is why the required set exists, and has not decided that reaching it from no configuration is right; this operator has no basis to decide that for them, and reads no key for something it could not deliver. What would settle it is an agent whose author needs to see or change the required set, rather than an operator asking for the switch on principle.
- **Whether an agent renews into a copy nothing refreshes.** ADR 0010 delivers the credential as a copy made once at pod start, which is the shape `garam`'s own chart renders and carries the same limitation. `garam`'s contract expects whatever refreshes such a copy to satisfy the arrival rule on every refresh, and nothing in this Pod refreshes it; the agent's mount is left writable so that the agent itself can. What would settle it is a measurement of what the adapter does with the file when it renews.
- **What runs beside the agent in the Pod this operator builds.** The workload carries one container, and the process that reads an agent's credential and carries its messages is a sidecar `garam` owns. Nothing here builds one, and what an agent image is expected to already contain — beyond running as the user the Pod names, which `spec.image` states — is not stated anywhere this repository can point at.
- **What an operator does when it learns it no longer holds an agent it is running.** The refusal reaches this operator only when it next needs a credential, and it acts on nothing: the credential in the Pod is the agent's to renew and `garam` publishes nothing that says an operator should stop. Whether the workload should be torn down, reported on, or left is undecided, and what would settle it is a reassignment happening to a running agent rather than to a test row.
- **Whether an agent's credential is ever replaced from this side.** An agent renews its own and this operator's route recovers one that expired, so the remedy exists and is unfenced. What is unmeasured here is whether the agent renews at all in practice and what it does when the file changes under it — its behaviour rather than this operator's.
- **No image here refuses a mode `garam` would.** The e2e suite runs a substitute image, and a substitute brings its own acceptance rules. The suite now applies `garam`'s rule to the delivered file itself, with a control the rule refuses, so the layer says whether the file would be accepted; what it still does not say is whether a `garam` process reads it, which needs an image that applies the rule at startup.
- **Whether an agent's image may write its own root filesystem.** `readOnlyRootFilesystem` is the part of the Pod's security context ADR 0006 left undecided that issue #85 did not settle with the rest. It is no part of PodSecurity `restricted`, so nothing refuses the workload without it; the manager sets it on itself and this operator sets it on neither container it builds, because the field constrains what an image needs rather than what it is allowed to do and neither image is this operator's — the agent's is the deployer's or the user's, and the copy tool's is the deployer's, asked for a shell and `install` and nothing more. Setting it on the init container alone would buy a guarantee about a filesystem discarded when that container exits, at the price of a third clause on `--agent-copy-image`. What would settle it is a deployment that has to refuse an agent image the right to write its own filesystem.
- **Resizing an agent's volume.** A StatefulSet's claim template is immutable after creation, so a change to `spec.storageSize` on an existing `Agent` cannot be satisfied by editing the workload. ADR 0005 accepts the limitation without answering it. The controller leaves the claim as it is and says so on the object, which makes the limitation visible without answering it either.
